# التحقق من هوية المنشأة الضريبية

هذه الإضافة لا تتجاوز reCAPTCHA ولا تستخدم صفحة الهيئة كواجهة API غير موثقة.
رابط التحقق اليدوي: https://zatca.gov.sa/ar/eServices/Pages/TaxpayerLookup.aspx

## التشغيل بالرابط فقط (الوضع الحالي)

لا يلزم اشتراك API للمسار اليدوي. يفتح المستخدم موقع الهيئة ويُدخل الرقم ويكمل
متطلبات الموقع بنفسه، ثم ينقل الاسم والرقم ويقر بمراجعة نتيجة التسجيل.
لا يقرأ التطبيق الصفحة آليًا ولا يجلب عنوانًا غير ظاهر في النتيجة.

- في العميل/المورد: يمكن استخدام الاسم والعنوان المنقولين يدويًا لتعبئة النموذج.
- في فاتورة المشتريات أو نافذة مراجعة AI: يجب تطابق النتيجة المنقولة مع اسم ورقم الفاتورة وسجل المورد.
- عند الحفظ والاعتماد، يعيد الخادم المطابقة ويسجل `manual_review` مع المستخدم الحالي ووقت الخادم والملاحظات.
- الإقرار لا يثبت أن البرنامج شاهد موقع الهيئة؛ هو إقرار بشري مصرح به، وليس تحقق API.
- لا يؤخذ الإقرار من حقول المستند المحفوظة أو من AI تلقائيًا؛ يُمرر بإجراء المستخدم الحالي عند الاعتماد.
- تغيير الاسم/الرقم في الواجهة يلغي الإقرار المعلق. لا يقوم الاعتماد الجماعي باختلاق إقرارات يدوية.

## الربط الآلي الاختياري لاحقًا

للجلب الآلي فقط يلزم وصول معتمد للتحقق من التسجيل، ثم محوّل خادمي يتبع العقد أدناه. هذا عقد
داخلي لهذا التطبيق، وليس وصفًا لواجهة ZATCA. لا يتم الجلب الحقيقي حتى يتوفر
المزوّد ويُنفّذ محوّله ويُختبر. بدون الإعداد يعرض التطبيق «لم يتم التحقق».

متغيرات الخادم فقط (لا تستخدم VITE_):

- `VAT_LOOKUP_ADAPTER_URL`: رابط HTTPS للمحوّل المعتمد.
- `VAT_LOOKUP_ADAPTER_TOKEN`: سر المصادقة الخاص به.

الطلب: POST، مع Bearer token، وجسم `{ "vatNumber": "15 digits" }`.
الاستجابة: `{ "vatNumber": "...", "status": "registered", "name": "legal name", "address": "optional" }`
أو `{ "vatNumber": "...", "status": "not_registered" }` فقط عند وجود نتيجة
قطعية من الجهة. الأخطاء وغياب البيانات يجب ألا تتحول إلى «غير مسجل».
لا ترسل ملفات الفواتير للمحوّل؛ يرسل الرقم وحده. يجب أن يجلب المحوّل نتيجة
حديثة، وألا يستنتج التسجيل من صيغة الرقم أو يستخدم بيانات نموذج لغوي.

## السلوك

- العميل/المورد: نقل الاسم والعنوان من النتيجة ثم تطبيقهما باختيار المستخدم.
- فاتورة الشراء: حقول للاسم والرقم الواردين في الفاتورة، ومقارنتهما بسجل المورد وبنتيجة الجهة.
- المسح الذكي وصندوق الوارد: التحقق مستقل عن استخراج AI، ويعاد قبل الاعتماد.
- التعارض أو عدم وجود تحقق آلي أو إقرار يدوي مطابق: حفظ مسودة فقط. اختلاف ترجمة الاسم يحتاج مراجعة؛ لا توجد مطابقة تقريبية تمنح اعتمادًا تلقائيًا.
- إدخال المستخدم في meta ليس دليل تحقق. دليل الاعتماد يكتبه الخادم وحده في جدول مغلق أمام المستخدمين.
- الدليل صالح 24 ساعة، ويبطل عند اختلاف رقم/اسم الفاتورة أو هوية المورد.

## ترتيب النشر

1. اختبار المسار اليدوي ببيانات اختبار؛ المحوّل الآلي غير مطلوب.
2. تطبيق `20260930190000_taxpayer_posting_checks.sql` مع نشر الواجهة في نافذة صيانة واحدة؛ الواجهة القديمة لا تتيح الإقرار المطلوب.
3. نشر كود التطبيق، ثم اختبار مستخدم عادي وSuper Admin.
4. اختبار إنشاء مسودة، اختلاف الاسم/الرقم، انقطاع المزوّد، وإعادة التحقق قبل الترحيل.

يمكن تشغيل ملف الترقية كاملًا في SQL Editor لمشروع Supabase الخاص بتطبيق كنار.
الملف يستخدم معاملة واحدة ومهلة انتظار قفل قدرها 5 ثوانٍ؛ عند أي خطأ لا تعتمد
التغييرات الجزئية، ونفّذ `ROLLBACK;` قبل إعادة المحاولة إن بقيت الجلسة في معاملة.
لا تشغّل سكربت تهيئة الخادم أو إنشاء مشروع جديد لهذه الترقية.
لا تنشر الفرع قبل تأكيد نجاح الترقية، ثم انشر مباشرة في نافذة الصيانة نفسها.

بعد الترقية يلزم تحقق API مطابق أو إقرار يدوي مطابق لاعتماد فواتير الشراء الجديدة،
مع إبقاء المسودات وقراءة المستندات القديمة متاحة. لم تُطبق هذه الترقية على قاعدة البيانات المنشورة.

الاختبارات المحلية: `node --test tests/accounting/taxpayer-verification.mjs`.
